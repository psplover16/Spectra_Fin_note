一鍵的定義

正規化全程都在問「哪個屬性被哪個屬性決定」、「誰是鍵」，先把鍵的術語釐清：

術語定義
外來鍵
Foreign Key		某欄位（或欄位組合），其值參考另一張表的主鍵，用來把兩張表串接、建立關聯
超鍵
Superkey		能唯一識別一列的欄位組合，可以帶多餘欄位
候選鍵
Candidate Key		最小的超鍵（拿掉任一欄就不再唯一）；每個都有資格當主鍵
主鍵
Primary Key		被選來唯一識別每筆紀錄的那一個候選鍵
替代鍵
Alternate Key		沒被選為主鍵的候選鍵
鍵（主）屬性
Prime		只要一個欄位屬於任何一個候選鍵，它就是鍵屬性
非鍵（主）屬性
Non-prime		不屬於任何候選鍵的欄位
💡 包含關係主鍵 ⊆ 候選鍵 ⊆ 超鍵。候選鍵是「最小的超鍵」，主鍵是「被選中的候選鍵」。另外，外來鍵也可以指向同一張表的主鍵（自我參考），例如員工表的「主管」欄位指向同表的員工編號。

二好的分解必備的兩個性質

（一）無損分解（Lossless-join）—— 必備

表格分解後，用自然合併組回去，結果與原表完全一樣：沒有遺失資料，也沒有多出虛假的資料組合。

  • 自然合併（Natural Join）：以兩表中同名且同型的欄位為合併條件，把這些欄位值相同的列組合起來；用來合併的同名欄位在結果中只保留一份。
  • 若兩表沒有同名欄位，自然合併會退化成笛卡兒乘積（每列兩兩相配）—— 這正是虛假資料的來源。
💡 無損其實「一定做得到」無損是硬性要求，而且永遠可達成：只要拆解時讓「共同欄位是其中一張子表的鍵」就保證無損。標準正規化的拆法（抽出「決定因素＋相依因素」、決定因素當新表主鍵、原表保留外來鍵）每一步本來就是無損，不需要靠反正規化補救。

（二）功能相依性保持（Dependency Preservation）—— 最好具備

分解前擁有的所有功能相依，於分解後的各子表中仍能保留與檢查（不必把表 join 回去才驗證）。

每條相依往往反映一條業務規則；若分解後失去，可能允許不合邏輯的操作、造成資料不一致。其與無損的差別：缺乏相依保持「不會」在分解當下產生虛假資料，但會讓後續的寫入／更新中，某些規則難以驗證與維持。

處理（無法保持時）：(1) 反正規化退回較低正規化（如 3NF）；或 (2) 在應用程式或觸發器（trigger）額外撰寫邏輯，於寫入／更新時檢查。

★ 最關鍵的一句（串起本節與 BCNF） 3NF 保證「無損」＋「功能相依性保持」兩者都有；BCNF 保證「無損」，但「功能相依性保持」不一定有。
這就是為什麼有時「停在 3NF 就好」：硬做到 BCNF 可能犧牲某條相依（規則），這時才用上面的反正規化／觸發器補回。

三正規化階梯（總覽）

正規化由低到高，每一階都比下一階多除去一種異常，且高階必須先滿足低階：

由下而上逐階加嚴；BCNF 介於 3NF 與 4NF 之間。做到某一階，前面各階都須已滿足

四第一正規化 1NF（除去重複資料項目）

要求：關聯表中每一個屬性的值皆具原子性，也就是非多值、非複合屬性。

處理方式：多值 → 分解成多個值組（多列）或另立表；複合屬性 → 拆為簡單屬性。

範例（違反 → 修正）

學號姓名電話
S01王小明0912-111、0922-222
S02李小華0933-333

問題：S01 的「電話」一格塞了兩個值，違反 1NF（欄位值不是單一值）。

處理後（把電話另立一張表，每格只放單一值）：

  • 學生（學號、姓名）
  • 學生電話（學號 FK、電話）　主鍵 = {學號, 電話}

五第二正規化 2NF（除去部分相依）

要求：滿足 1NF，且每個非鍵屬性都「完全功能相依」於鍵（即沒有部分相依）。

處理方式：把部分相依的非鍵屬性，連同其決定因素抽出、建立新關聯（決定因素當新表主鍵），原表刪除該相依因素，並設外來鍵。

💡 兩個精確化① 嚴格定義是針對候選鍵，非只有主鍵；寫「主鍵」考試多半可接受，但碰到多候選鍵的題目要用候選鍵。② 部分相依只可能發生在「複合鍵」——主鍵若是單一屬性，沒有「一部分」可被相依，自動滿足 2NF。

範例（違反 → 修正）

原表：選課（學號, 課號, 成績, 課名），主鍵 = {學號, 課號}。功能相依：

  • {學號, 課號} → 成績　需要兩個鍵才能決定 → 完全相依（OK）
  • 課號 → 課名　只靠課號就能決定 → 部分相依（違反 2NF）

為何違反：課名只依賴主鍵的「一部分」（課號），不是整個主鍵。

處理後（把「課號＋課名」抽出另立表，原表保留課號當外來鍵）：

  • 選課（學號、課號、成績）　主鍵 = {學號, 課號}；課號 為 FK → 課程
  • 課程（課號、課名）

六第三正規化 3NF（除去遞移相依）

要求：滿足 2NF，且不存在非鍵屬性遞移相依於鍵；也就是非鍵屬性之間不存在功能相依（非鍵屬性不互相決定）。

處理方式：把遞移相依中「非鍵的決定因素＋其相依因素」抽出、建立新關聯，原表刪除相依因素，並設外來鍵。

💡 形式定義（進階）對每一條非顯然相依 X → A：X 是超鍵，或 A 是主屬性。注意這個「或 A 是主屬性」的例外，就是 3NF 與 BCNF 的分水嶺（見下節）。

範例（違反 → 修正）

原表：學生（學號, 系所, 系主任），主鍵 = {學號}。功能相依：

  • 學號 → 系所（學生屬於某系）
  • 系所 → 系主任（系決定系主任）
  • ⇒ 推得 學號 → 系主任，為遞移相依

為何違反：系主任（非主屬性）是透過「系所」間接依賴主鍵，即依賴另一個非主屬性。

處理後（把「系所＋系主任」抽出另立表，原表保留系所當外來鍵）：

  • 學生（學號、系所 FK）
  • 系所（系所、系主任）

七BCNF（Boyce-Codd 正規化）

定義：屬於 3NF 的加強，一定符合 3NF。要求每一條非顯然功能相依的決定因素皆為超鍵。

★ BCNF 真正嚴在哪（不是超鍵 vs 候選鍵） 比較兩者對每條 X → A 的要求：
・3NF：X 是超鍵 或 A 是主屬性　←　有一個「逃生門」
・BCNF：X 是超鍵　←　拿掉了「或 A 是主屬性」這個逃生門
兩者用的都是「超鍵」。BCNF 更嚴，是因為它取消了 3NF「被決定的是主屬性就放行」的例外。（順帶一提：「超鍵」比「候選鍵」更寬，候選鍵本來就是超鍵的一種，所以用超鍵不是收緊。）

何時 3NF 與 BCNF 才會不同

只有在表中存在多個、互相重疊的複合候選鍵時，兩者才會不同。若一張表只有單一候選鍵（尤其是單一屬性），那它只要是 3NF 就自動是 BCNF。

經典例：符合 3NF 但違反 BCNF

指導（學生, 科目, 老師），已知 {學生,科目} → 老師、老師 → 科目。候選鍵為 {學生,科目} 與 {學生,老師}（重疊在「學生」），故學生、科目、老師皆為主屬性。

  • 檢查 老師 → 科目：老師不是超鍵，但科目是主屬性 → 符合 3NF。
  • 同一條 老師 → 科目：老師不是超鍵 → 違反 BCNF。

處理方式

  • A. 拆解關聯：把「不為超鍵的決定因素＋其相依因素」抽出、建立新關聯，原表刪除相依因素。
  • B. 決定外來鍵。

依違反的 老師 → 科目 拆解後：

  • 授課（老師、科目）
  • 指導（學生、老師）
💡 BCNF 的代價此分解無損，但不保功能相依性保持：原相依 {學生,科目} → 老師 會跨兩張表、無法保存——這正是「停在 3NF」的取捨點。

八4NF、5NF 與反正規化

第四正規化 4NF

滿足 BCNF，且不存在多值相依（Multivalued Dependency）。多值相依：一個鍵決定某屬性的「一組值」，且該組值與另一獨立屬性互不相干。例：員工有多個技能、又有多個語言，兩者彼此獨立 → 應拆成「員工–技能」與「員工–語言」兩表，避免兩兩交叉產生冗餘。

第五正規化 5NF

滿足 4NF，且不存在無法由候選鍵推得的合併相依（Join Dependency）。處理：拆成更小的投影，使其能無損合併還原。（國考多僅須知定義與層級）

反正規化（Denormalization）

為了查詢效能，刻意違反正規化、加入冗餘（如預先 join 好、加入計算欄位），以減少 join、加快讀取；代價是增加冗餘與更新異常風險。常用於讀多寫少、報表查詢的場景。

九結論

正規化以拆解消除資料異常：1NF（原子性）、2NF（去部分相依）、3NF（去遞移相依）、BCNF（決定因素皆超鍵），再上有 4NF（多值相依）、5NF（合併相依）。好的分解必須無損（必備）、最好保持功能相依；其中 3NF 兩者兼得、BCNF 保無損但相依保持不一定，這是實務「做到哪一階」與是否反正規化的取捨依據。

⚠️ 考點提醒
  • 包含關係：主鍵 ⊆ 候選鍵 ⊆ 超鍵；鍵屬性＝屬於任一候選鍵的屬性。
  • 無損分解＝必備（join 回去與原表相同、無虛假列）；無同名欄位 → 退化成笛卡兒乘積。
  • 功能相依性保持＝最好有；缺它不會當下產生虛假資料，但後續規則難維持。
  • 3NF 保證 無損＋相依保持；BCNF 保證無損，但相依保持不一定。
  • 1NF 原子性、2NF 去部分相依（只發生在複合鍵）、3NF 去遞移相依、4NF 去多值相依、5NF 去合併相依。
  • BCNF：每個決定因素皆為超鍵；它比 3NF 嚴，是少了「或 A 是主屬性」的例外。3NF≠BCNF 只在重疊的複合候選鍵時發生。
