## 系統分析與設計這科在考什麼

系統分析與設計（Systems Analysis and Design）是研究「如何把使用者的需求，轉成可以開發、維護、管理的資訊系統」的一門科目。白話來說，它不是只考寫程式，而是考你是否知道一個資訊系統從想法、需求、分析、設計、建置、測試到維護，應該怎麼一步一步完成。

資訊系統（Information System）是由人員、資料、流程、軟體、硬體與網路共同組成，用來支援組織作業與決策的系統。國考常會用「企業要導入新系統」「舊系統要改善」「使用者需求不清楚」這類情境，要求考生說明該如何分析、設計或選擇方法。

系統開發生命週期（System Development Life Cycle, SDLC）是本科技術主軸之一，意思是資訊系統從規劃到維護的完整流程。常見階段包含：

1. 規劃（Planning）：確認問題、目標、範圍與可行性。
2. 分析（Analysis）：了解使用者需求與現行作業流程。
3. 設計（Design）：規劃系統架構、資料、介面、流程與控制機制。
4. 實作（Implementation）：開發、測試、導入與轉換。
5. 維護（Maintenance）：修正錯誤、改善功能與適應環境變化。

這科的核心想法是：系統不是憑空寫出來的，而是從問題開始，經過需求釐清與設計取捨，最後才變成可運作的資訊系統。

## 新手為什麼會覺得抽象

系統分析與設計常讓新手覺得難，是因為它不像計算題有明確公式，也不像法科有固定條文。很多題目問的是「方法」「流程」「差異」「優缺點」與「適用情境」。

例如題目可能問：

- 瀑布模式（Waterfall Model）與敏捷開發（Agile Development）的差異。
- 需求分析（Requirements Analysis）為什麼重要。
- 原型法（Prototyping）適合什麼情境。
- 系統分析師（Systems Analyst）在專案中扮演什麼角色。

如果沒有實務經驗，這些名詞一開始會像一串抽象標籤。但國考準備不需要先變成專案經理，也不需要先做過大型系統。比較有效的方式，是先用歷屆題目找出常考範圍，再把每個名詞整理成「定義、用途、優點、缺點、適用情境、易混淆對象」。

## 最有效的準備順序

### 1. 先看歷屆題目，抓出常考主題

歷屆題目是準備本科技最重要的入口。因為系統分析與設計範圍廣，如果一開始就從課本第一頁讀到最後一頁，很容易讀很多卻不知道考點在哪裡。

建議先把歷屆題目分成幾類：

1. 開發方法：例如瀑布模式、敏捷開發、螺旋模式、原型法。
2. 需求分析：例如需求蒐集、需求確認、使用者訪談、使用案例。
3. 系統設計：例如資料庫設計、介面設計、輸入輸出設計、控制設計。
4. 建模工具：例如資料流程圖（Data Flow Diagram, DFD）、實體關係模型（Entity-Relationship Model, ER Model）、統一塑模語言（Unified Modeling Language, UML）。
5. 專案管理：例如成本、時程、風險、品質、人員溝通。
6. 系統導入與維護：例如轉換方式、測試方法、維護類型。

這樣讀書會比較有方向，因為你會知道哪些名詞不是冷知識，而是國考常拿來出題的核心素材。

### 2. 名詞先定義，再背考法

重要名詞不要只背中文翻譯。每個名詞至少要掌握四件事：

1. 它是什麼。
2. 它用來解決什麼問題。
3. 它的優點與限制。
4. 它常和誰比較。

例如原型法（Prototyping）是先快速做出可展示或可操作的雛形，讓使用者提早看到系統可能長什麼樣子，再根據回饋修正需求與設計。它的核心價值是降低需求不明確造成的風險。

具體範例：某機關想做線上申辦系統，但承辦人一開始說不清楚表單欄位與審核流程。此時可以先做一個簡化版畫面，讓承辦人試用後指出缺少哪些欄位、流程哪裡不順，再逐步修正。

國考考法通常會問：原型法適合需求不明確、使用者難以描述需求、需要快速回饋的情境；但缺點是容易讓使用者誤以為雛形就是正式系統，也可能造成文件不足或範圍擴張。

### 3. 比較題要整理成表格

比較題是本科技常見題型。看到兩個相似名詞時，不要只各背各的定義，要主動整理差異。

例如瀑布模式（Waterfall Model）是依照階段順序進行的開發模式，每個階段完成後才進入下一階段。敏捷開發（Agile Development）則是強調短週期、持續回饋、快速調整與可運作軟體交付的開發方式。

| 比較項目 | 瀑布模式（Waterfall Model） | 敏捷開發（Agile Development） |
| --- | --- | --- |
| 核心想法 | 階段明確、依序完成 | 反覆迭代、快速回饋 |
| 適合情境 | 需求穩定、變動少 | 需求容易改變、需要快速交付 |
| 優點 | 文件完整、管理清楚 | 彈性高、能及早回應使用者 |
| 缺點 | 後期修改成本高 | 需要高度溝通與自律 |
| 國考關鍵字 | 順序、文件、控制 | 迭代、增量、回饋、彈性 |

答申論題時，可以先寫兩者定義，再用比較表或分點說明差異，最後補上適用情境。這樣答案會比單純列名詞更完整。

## 重要組成與準備重點

### 系統分析

系統分析（Systems Analysis）是釐清問題、需求、流程與限制的工作。它回答的是：「這個系統到底要解決什麼問題？」

核心想法是先理解業務，再談技術。如果需求分析做不好，後面即使程式寫得很漂亮，也可能做出使用者不需要的系統。

常見工具包含：

1. 訪談（Interview）：直接與使用者或主管談需求。
2. 問卷（Questionnaire）：大量蒐集使用者意見。
3. 觀察（Observation）：實際觀看工作流程。
4. 文件分析（Document Analysis）：閱讀表單、報表、規章與舊系統資料。
5. 使用案例（Use Case）：描述使用者如何與系統互動以完成目標。

國考常問需求蒐集方法的優缺點。例如訪談可以深入了解問題，但耗時且受訪者可能表達不完整；問卷可以快速蒐集大量資料，但不容易追問細節。

### 系統設計

系統設計（Systems Design）是把分析階段得到的需求，轉成系統規格與技術方案。它回答的是：「這個系統要怎麼做出來？」

系統設計通常包含：

1. 架構設計（Architecture Design）：決定系統元件如何分工與連接。
2. 資料設計（Data Design）：規劃資料表、欄位、關聯與資料品質。
3. 介面設計（Interface Design）：規劃使用者如何操作系統。
4. 輸入設計（Input Design）：規劃資料如何進入系統。
5. 輸出設計（Output Design）：規劃報表、查詢結果與通知。
6. 控制設計（Control Design）：規劃權限、稽核、錯誤檢查與安全機制。

具體範例：如果要設計一個報名系統，系統分析會先問「誰要報名、報名流程是什麼、要收哪些資料」；系統設計則會進一步決定「報名資料表怎麼設計、畫面欄位怎麼排、重複報名如何檢查、管理者如何匯出名單」。

國考常把分析與設計放在一起考。簡單判斷是：問「要做什麼」偏系統分析；問「如何做」偏系統設計。

### 建模工具

建模（Modeling）是用圖形或結構化方式描述系統。它的目的不是畫漂亮的圖，而是幫助分析人員、設計人員與使用者溝通。

資料流程圖（Data Flow Diagram, DFD）是描述資料如何在處理程序、資料儲存、外部實體之間流動的圖。它重視資料流向與處理程序。

實體關係模型（Entity-Relationship Model, ER Model）是用來描述資料實體、屬性與關係的模型。它常用於資料庫設計。

統一塑模語言（Unified Modeling Language, UML）是一套物件導向系統建模語言，常見圖形包含使用案例圖、類別圖、循序圖與活動圖。

國考常見考法是要求說明某種圖的用途，或比較不同圖形適合描述什麼面向。答題時要抓住重點：DFD 看資料流，ER Model 看資料結構，UML 看物件與互動。

## 國考常見考法

本科技考題常不是問「請背出某段課本文字」，而是把名詞放進情境中考判斷。

常見題型包含：

1. 名詞解釋題：要求說明 SDLC、DFD、UML、需求分析、原型法等。
2. 比較題：要求比較瀑布模式與敏捷開發、白箱測試與黑箱測試、直接轉換與平行轉換。
3. 流程題：要求說明系統開發流程、需求分析流程、系統導入流程。
4. 優缺點題：要求說明某方法的好處、限制與適用情境。
5. 情境應用題：給一個機關或企業案例，要求選擇適當開發方法或分析工具。

準備時可以把每個主題整理成固定答題模板：

1. 先定義名詞。
2. 說明核心想法。
3. 補一個具體例子。
4. 寫出優點、缺點或適用情境。
5. 若題目要求比較，就用表格或分點列出差異。

## 易混淆整理

| 易混淆項目 | 重點差異 | 國考判斷技巧 |
| --- | --- | --- |
| 系統分析（Systems Analysis）與系統設計（Systems Design） | 分析重在需求與問題，設計重在規格與解法 | 「要做什麼」是分析；「怎麼做」是設計 |
| DFD 與 ER Model | DFD 看資料流動，ER Model 看資料結構 | 有處理程序與資料流，多半是 DFD；有實體、屬性、關係，多半是 ER Model |
| 瀑布模式與敏捷開發 | 瀑布重階段順序，敏捷重迭代回饋 | 需求穩定選瀑布；需求變動選敏捷 |
| 原型法與正式系統 | 原型是用來溝通與確認需求的雛形，正式系統才是可長期運作的產品 | 題目出現「需求不清楚、先讓使用者看」常考原型法 |
| 需求分析與程式設計 | 需求分析釐清使用者需要什麼，程式設計負責實作功能 | 不要把「訪談使用者」誤判成寫程式 |

## 國考必背整理

1. 系統分析與設計（Systems Analysis and Design）重點是把使用者需求轉成可實作、可維護的資訊系統。
2. 系統開發生命週期（System Development Life Cycle, SDLC）通常包含規劃、分析、設計、實作與維護。
3. 需求分析（Requirements Analysis）做不好，後續開發容易產生返工、成本增加與使用者不滿。
4. 瀑布模式（Waterfall Model）適合需求穩定、階段明確、重視文件與控制的專案。
5. 敏捷開發（Agile Development）適合需求變動快、需要使用者持續回饋與快速交付的專案。
6. 原型法（Prototyping）適合需求不明確、使用者難以一次說清楚需求的情境。
7. 資料流程圖（Data Flow Diagram, DFD）重點是資料如何流動與被處理。
8. 實體關係模型（Entity-Relationship Model, ER Model）重點是資料實體、屬性與關係。
9. 統一塑模語言（Unified Modeling Language, UML）常用於物件導向分析與設計。
10. 比較題要寫出定義、差異、優缺點與適用情境，不能只背名詞。

## 容易考的判斷題

1. 如果題目說需求尚未明確，但希望使用者先看到雛形並提供回饋，通常適合原型法（Prototyping）。
2. 如果題目說需求穩定、文件要求高、每個階段需要正式審查，通常偏向瀑布模式（Waterfall Model）。
3. 如果題目強調短週期交付、持續回饋、快速調整，通常偏向敏捷開發（Agile Development）。
4. 如果題目問資料在系統中如何流動，通常會連到資料流程圖（Data Flow Diagram, DFD）。
5. 如果題目問資料庫中資料表或資料實體如何關聯，通常會連到實體關係模型（Entity-Relationship Model, ER Model）。
6. 如果題目問使用者如何透過系統完成某個目標，通常會連到使用案例（Use Case）。
7. 如果題目問系統開發一開始如何確認問題、目標與可行性，通常是在考規劃（Planning）。
8. 如果題目問如何把需求轉成資料、介面、架構與控制規格，通常是在考系統設計（Systems Design）。

## 考前速記小抄

系統分析與設計這科的讀法，可以記成一句話：先用歷屆題目抓範圍，再用名詞定義打底，最後用比較表練考法。

考前複習時，請特別注意：

1. 看到名詞，要能說出「定義、用途、優缺點、適用情境」。
2. 看到兩個相似名詞，要能整理成比較表。
3. 看到情境題，要先判斷關鍵字，再選方法。
4. 不確定從哪裡開始時，先讀歷屆題目中反覆出現的主題。
5. 不要只背零散名詞，要把名詞放回 SDLC 的階段中理解。

最重要的是，本科不需要一開始就全部讀懂。先從常考題目出發，逐步累積名詞與比較題，抽象內容就會慢慢變成可以作答的架構。
