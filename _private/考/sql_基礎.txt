ANSI/SPARC 是一種三層式資料庫架構，核心目的在於將「使用者應用程式」與「實體資料儲存」完全分離，藉此達成「資料獨立性」（Data Independence）。
由使用者端至實體儲存端劃分為三層：
    1. 外部層，又稱「視界層」。
        最接近使用者。僅呈現特定使用者所需要的局部資料，隱藏其餘無權或不須知道的部分，以簡化操作並提升安全性。
    2. 概念層，又稱「邏輯層」。
        描述整個資料庫的邏輯全貌（包含資料實體、關聯性與限制條件）。它整合了所有外部需求，隱藏底層儲存細節，通常由資料庫管理員負責設計。
    3. 內部層，又稱「實體層」。
        最接近硬體。描述資料在磁碟上的實際儲存方式，包含檔案結構、資料壓縮、存取路徑與索引技術，以追求系統效能最佳化。
系統透過層與層之間的「對應機制」來達成資料獨立性：
    1. 外部/概念對應，
        1. 欲達成目標為「邏輯資料獨立性」。
        2. 當「概念層」的邏輯結構發生變更（如新增資料表或欄位）時，只需修改此對應關係，使用者的「外部層」與應用程式皆無須修改。
    2. 概念/內部對應 (Conceptual/Internal Mapping)
        1. 欲達成目標為「實體資料獨立性」。
        2. 當「內部層」的實體儲存結構變更（如更換儲存設備、更改索引方式）時，只需修改此對應關係，「概念層」與「外部層」皆無須修改。此種獨立性較易達成。

資料庫的種類
1. 階層式資料庫
    1. 樹狀
    2. 一對多，1:N
    3. 以指標沿樹狀路徑存取。
    4. 結構簡單、查詢快；但無法表達 M:N、結構僵硬、資料易重複。
2. 網路式資料庫
    1. 圖狀
    2. 可M:N
    3. 以指標連結。
    4. 較階層式靈活；但結構更複雜、指標維護困難、程式與結構耦合高。
3. 關聯式資料庫
    1. 二維表格
    2. 以「值」（外來鍵）建立表間關聯，而非指標。
    3. 簡單直覺、理論嚴謹、資料獨立性高、查詢彈性強；
    4. 但複雜關聯需大量 JOIN、不擅長非結構化資料、大規模水平擴展較難。
4. 物件導向式資料庫
    1. 以物件儲存
    2. 支援封裝、繼承、多型，每個物件有唯一識別碼。
    3. 直接對應物件導向程式、解決阻抗不匹配、擅長複雜資料；但標準不統一、學習曲線高、市場接受度低。
(阻抗不匹配，物件導向程式的「物件」與關聯式的「表格」結構不一致，存取時須來回轉換)

    REVOKE INSERT ON company.employees FROM 'username'@'%';

    REVOKE ALL PRIVILEGES ON company.employees FROM 'username'@'192.168.1.50';

    REVOKE GRANT OPTION ON company.employees FROM 'username'@'192.168.1.50';

SELECT 
    部門名稱,
    COUNT(員工ID) AS 總人數,           -- 計算：這個部門有幾個人？
    ROUND(SUM(薪資), 2) AS 總薪資支出,   -- 計算：老闆每個月要發多少錢給這個部門？
    AVG(薪資) AS 平均薪資,             -- 計算：這個部門的平均水準在哪？
    MAX(薪資) AS 最高薪,               -- 計算：這個部門裡的最高薪（通常是主管）是多少？
    MIN(薪資) AS 最低薪,               -- 計算：這個部門裡的最低薪（通常是菜鳥）是多少？
    
    -- 【新增：算術運算子示範 (+, -, *, /, %)】
    MAX(薪資) - MIN(薪資) AS 薪資高低差,                 -- [- 減法]：高低薪水差多少
    AVG(薪資 * 12 + 考核獎金) AS 預估平均年薪,             -- [* 乘法, + 加法]：月薪乘12個月加獎金
    SUM(薪資) / COUNT(員工ID) AS 驗算平均薪,             -- [/ 除法]：總薪資除以人數
    MAX(薪資 % 1000) AS 最高薪的尾數零頭                 -- [% 取餘數]：除以 1000 剩下的零頭
    
FROM 員工表

-- 【新增：比較與邏輯運算子示範】
WHERE 職級 NOT IN ('實習生', '工讀生')          -- [NOT IN]：排除這兩個特定身分
  AND 薪資 BETWEEN 30000 AND 150000            -- [BETWEEN AND]：薪水必須落在 3萬 到 15萬 之間
  AND 員工姓名 LIKE '王%'                       -- [LIKE]：模糊搜尋，只找姓「王」的 ( % 代表後面接任意字元)
  AND 離職日期 IS NULL                          -- [IS NULL]：檢查欄位是否為空 (沒有離職日期 = 仍在職)
  AND (績效分數 >= 80 OR 年資 > 3)              -- [>=, OR, >]：績效80分以上，或者年資大於3年 (用括號包住優先運算)
  AND 部門代號 <> 999                           -- [<> 或 !=]：不等於 999 (管理高層的隱藏代號)

   AND AVG(薪資) < 80000                -- [<]：且該部門平均薪資不能超過 8 萬

交易是資料庫中一個不可分割的工作單位，由一連串操作組成。其核心精神為「全部成功」或「全部失敗」。
原子性 (Atomicity)：交易中所有操作「全部完成」或「全部不做」；失敗時以 ROLLBACK 復原。
一致性 (Consistency)：交易執行前後，資料庫都維持在符合所有完整性限制的合法狀態，此為終極目標。
隔離性 (Isolation)：多個交易並行時互不干擾，一交易的中間結果不被其他交易看見。此特性以鎖定（Locking）或 MVCC 達成。
    隔離性負責處理「時間順序與併發排隊」，把「同時發生」的混亂交易，排隊執行。
持久性 (Durability)：交易一旦 COMMIT，變更即永久保存，即使系統故障也不遺失；以交易記錄檔（log）達成。
核心公式：原子性 (A) + 隔離性 (I) + 持久性 (D) = 一致性 (C)。


讀取異常 (難以預防度：髒讀 < 不可重複讀 < 幻讀)
髒讀 (Dirty Read)：讀到另一交易「未提交」的資料。
不可重複讀：在同一交易內前後讀取同一筆資料，卻因其他交易在期間內完成「更新 (Update) 或刪除 (Delete)」，導致兩次讀取的數值或狀態不一致。
幻讀 (Phantom Read)：在同一交易內前後執行相同的範圍查詢，卻因其他交易在期間內「新增 (Insert)」或「刪除 (Delete)」了符合條件的紀錄，導致第二次查詢得到的資料與之前不相同。幻讀僅靠序列化才能防禦。

隔離等級
Read Uncommitted (讀未提交)：無防禦力。
Read Committed (讀已提交)：防髒讀。
Repeatable Read (可重複讀)：MySQL 預設。防不可重複讀。
Serializable (序列化)：強制循序排隊。效能極差，防所有異常 (含幻讀)。

隔離性（Isolation）的實作：
MVCC (多版本併發控制)，是一種資料庫系統用於處理並行控制的技術。
    核心概念：資料修改時不直接覆蓋，而是保留歷史版本，使不同交易能讀取當前有效的快照，達成「讀寫互不阻塞」的底層機制。
    特性：
        讀不阻塞寫，寫不阻塞讀：查詢操作讀取歷史快照，更新操作則修改最新版本。雙方互不干擾。
        空間換時間：儲存歷史快照佔用空間，換取免等待的執行速度。
    MVCC 在 RR 與 RC 的決定性差異
        RC 等級：每次執行 SELECT 都會產生一個「全新的快照」。
            因此，若別的交易剛 COMMIT，你只要再次執行 SELECT，就會讀到別人改過的最新資料（無法防禦不可重複讀）。
        RR 等級：第一次 SELECT 產快照，後續沿用舊快照 (達成可重複讀)。
樂觀併發控制 (OCC, Optimistic Concurrency Control / 樂觀鎖)
    秉持「事後檢查」的無鎖（Lock-free）策略，假設交易間發生衝突的機率極低。
    運作說明：在交易執行的過程中，不會阻擋任何其他交易的讀寫操作。
      直到交易準備執行 UPDATE 或 COMMIT 的最後一刻，
      才透過比對「版本號（Version）」或「時間戳記（Timestamp）」，來核對資料是否已被他人竄改。
      若發現衝突，則拒絕更新並讓交易失敗（Rollback），交由應用程式決定是否重試。
鎖定機制 (Locking / 悲觀鎖)
    透過對資料施加限制來控制存取。
    當發生衝突時，會強制其他交易「排隊等待」，是一種「以時間換取正確性」的作法。
    為了保證交易的衝突可序列化，此機制必須嚴格遵守二階段鎖定協定（2PL）。
        共享鎖（S-Lock，允許多人同時唯讀），FOR SHARE
        排他鎖（X-Lock，僅限一人獨佔讀寫），FOR UPDATE

1. A 交易先 FOR UPDATE，B 交易執行普通 SELECT 是可以的，因為根本不會去申請任何鎖，而是直接觸發 MVCC 機制。
    繞過 A 交易鎖住的真實數據，跑去底層的 Undo Log (回滾日誌) 拿這筆資料上鎖前的「舊照片」來看。
2. 但其他 FOR UPDATE、FOR SHARE、UPDATE、DELETE 會被禁止，因為這四個指令在 MySQL 底層統稱為「當前讀 (Current Read)」
    FOR SHARE會試圖申請X-LOCK，而其他指令則試圖申請 X-Lock
3. 同一筆交易，FOR UPDATE 先，可以兼容 FOR UPDATE，也可以做其他等級的 SELECT。
4. 同一筆交易，先 FOR SHARE，若使用 UPDATE，則鎖會升級（鎖只會升級）。
5. 盡量避免先 SHARE 再 UPDATE。
    若交易 A 與 B 同時對同一筆資料下 FOR SHARE (皆取得 S-Lock)，隨後雙方都要求 UPDATE (要求升級為 X-Lock)，雙方會互相等待對方釋放 S-Lock，直接引發死結。若確定要改，建議一開始就直接 FOR UPDATE。


二階段鎖定協定 (Two-Phase Locking Protocol, 2PL)：
    是一種併發控制機制，用來確保多個交易 (Transaction) 並行時，結果能保證「衝突可序列化 (Conflict Serializable)」。 (排隊循序執行)    
標準 2PL 兩大階段，交易的鎖定行為必須嚴格遵守以下兩階段，且絕對不能交錯：
    擴張階段 (Growing Phase)：交易只能不斷「申請新鎖」，絕對不可釋放任何鎖。
    收縮階段 (Shrinking Phase)：一旦釋放了「第一個鎖」即進入此階段。交易只能「釋放鎖」，絕對不可申請新鎖。
【標準 2PL 的缺點】 雖能保證可序列化，但實務上有兩大缺陷：
    1. 連鎖復原 (Cascading Rollback)：(最致命缺點) 允許在 COMMIT 前提早解鎖。
        若交易最終 ROLLBACK，會導致讀到半成品資料的其他交易也被迫取消，引發效能災難。
    2. 無法避免死結 (Deadlock)：交易在擴張期可能互相等待對方手上的鎖，導致永久卡死。

【嚴格二階段鎖定 (Strict 2PL)】 為解決連鎖復原，現代資料庫（如 MySQL, SQL Server）皆強制採用此改良版：
    所有的排他鎖 (X-Lock) ，直到交易發出 COMMIT 或 ROLLBACK 的那一刻，才一口氣全部釋放。
核心優點：確保未提交的修改不會外洩，徹底解決連鎖復原問題。
【嚴格 2PL 的缺點】 雖解決了連鎖復原，但也付出了效能代價：
併發度大幅下降 (Reduced Concurrency)：鎖被強制扣留到最後一刻，其他交易等待時間變長，導致系統整體吞吐量 (Throughput) 下降。
死結機率更高：因鎖抓得比標準 2PL 更久，發生鎖競爭與死結的機率隨之增加。



【嚴格二階段鎖定 (Strict 2PL)】 是標準 2PL 的改良版。
    1. 交易中所取得的排他鎖 (X-Lock)，直到交易發出 COMMIT 或 ROLLBACK 的那一刻，才一口氣全部解開。
    2. 能徹底解決『連鎖復原 (Cascading Rollback)』的災難。
        因為寫入鎖被扣留到最後一刻，其他交易絕對無法讀取到『尚未提交的半成品資料（避免髒讀）』。
        因此，當該交易失敗需要復原時，絕不會連累其他交易跟著被迫復原，確保了資料庫的穩定性。」
    3. 雖然解決連鎖復原，但也付出效能代價：
        1. 併發度驟降 (Reduced Concurrency)：因為鎖被強制霸佔到最後一刻，其他交易的等待時間被迫拉長，導致系統整體的吞吐量 (Throughput) 大幅下降。
        2. 死結 (Deadlock) 機率提高：因為每個交易都把鎖抓得更久不放，發生『互相等待對方放鎖』的鎖競爭機率自然會大幅增加。」
