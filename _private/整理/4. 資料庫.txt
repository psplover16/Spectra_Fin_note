ANSI/SPARC
一、 核心概念
ANSI/SPARC 是一種三層式資料庫架構，核心目的在於將「使用者應用程式」與「實體資料儲存」完全分離，藉此達成「資料獨立性」（Data Independence）。
二、 三層架構解析
由上（使用者端）至下（實體儲存端）劃分為三層：
  1. 外部層 (External Level / View Level)，又稱「視界層」。
    最接近使用者。僅呈現特定使用者所需要的局部資料，隱藏其餘無權或不須知道的部分，以簡化操作並提升安全性。
  2. 概念層 (Conceptual Level / Logical Level)，又稱「邏輯層」。
    描述整個資料庫的邏輯全貌（包含資料實體、關聯性與限制條件）。它整合了所有外部需求，隱藏底層儲存細節，通常由資料庫管理員 (DBA) 負責設計。
  3. 內部層 (Internal Level / Physical Level)，又稱「實體層」。
    最接近硬體。描述資料在磁碟上的實際儲存方式，包含檔案結構、資料壓縮、存取路徑與索引技術，以追求系統效能最佳化。
三、 兩層對應 (Mapping) 與資料獨立性
系統透過層與層之間的「對應機制」來達成資料獨立性：
  1. 外部/概念對應 (External/Conceptual Mapping)
    欲達成目標為「邏輯資料獨立性」。
    當「概念層」的邏輯結構發生變更（如新增資料表或欄位）時，只需修改此對應關係，使用者的「外部層」與應用程式皆無須修改。
  2. 概念/內部對應 (Conceptual/Internal Mapping)
    欲達成目標為「實體資料獨立性」。
    當「內部層」的實體儲存結構變更（如更換儲存設備、更改索引方式）時，只需修改此對應關係，「概念層」與「外部層」皆無須修改。此種獨立性較易達成。

資料庫優缺點及種類：
一. 資料庫問世前，資料分散儲存於各應用程式的獨立檔案中，造成資料重複與不一致；資料庫系統將資料集中管理，以解決上述問題。
二. 優缺點
  優點
    1. 降低資料重複（Reduce Redundancy）：資料集中存放，避免同一資訊重複儲存。
    2. 維持資料一致性（Consistency）：減少重複，即降低前後不一致的風險。
    3. 資料共享（Data Sharing）：多使用者、多應用程式可同時存取同一份資料。
    4. 維護資料完整性（Integrity）：以完整性限制（如鍵、CHECK）確保資料正確。
    5. 強化安全性（Security）：以權限控管限制不同使用者的存取範圍。
    6. 提供資料獨立性（Data Independence）：分為邏輯與實體獨立性（見講義 01）。
    7. 備份與復原（Backup & Recovery）：故障後可回復至一致狀態。
    8. 並行控制（Concurrency Control）：多使用者同時操作而不互相破壞。
  缺點：
    1. 成本高：軟硬體、授權費用與專業人員（DBA）成本可觀。
    2. 系統複雜：設計、調校與維護需要專業知識。
    3. 效能負擔（Overhead）：為兼顧安全、一致與並行控制，會犧牲部分效能。
    4. 集中化風險：資料集中導致單點故障（Single Point of Failure），一旦損毀影響範圍大。
三. 種類
  1. 階層式資料庫，
    1. 樹狀，
    2. 一對多，1:N，
    3. 以指標沿樹狀路徑存取。
    4. 結構簡單、查詢快；但無法表達 M:N、結構僵硬、資料易重複。
  2. 網路式資料庫，
    1. 圖狀，
    2. 可M:N，
    3. 以指標連結。
    4. 較階層式靈活；但結構更複雜、指標維護困難、程式與結構耦合高。
  3. 關聯式資料庫，
    1. 二維表格，
    2. 以「值」（外來鍵）建立表間關聯，而非指標。
    3. 簡單直覺、理論嚴謹、資料獨立性高、查詢彈性強；但複雜關聯需大量 JOIN、不擅長非結構化資料、大規模水平擴展較難。
  4. 物件導向式資料庫，
    1. 以物件儲存，
    2. 支援封裝、繼承、多型，每個物件有唯一識別碼。
    3. 直接對應物件導向程式、解決阻抗不匹配、擅長複雜資料；但標準不統一、學習曲線高、市場接受度低。
      (阻抗不匹配，物件導向程式的「物件」與關聯式的「表格」結構不一致，存取時須來回轉換)

基礎
一. 鍵（Key）是用來唯一識別關聯表中某一列（tuple／紀錄）的欄位或欄位組合。
  1. 超鍵(Superkey)能唯一識別資料表中每一筆紀錄的欄位集合（可能包含多餘欄位）。
  2. 候選鍵(Candidate Key) 具備「最小性」的超鍵（不含多餘欄位）
  3. 主鍵(Primary Key) 設計者從「候選鍵」中挑選出一個，作為代表該表唯一識別的鍵（絕對不可為 NULL）。
  4. 替代鍵(Alternate Key) 未被選為主鍵的其餘「候選鍵」。
  5. 外來鍵(Foreign Key)用來參照另一個資料表主鍵的欄位，目的是建立兩表關聯，並確保「參考完整性」。
  6. 複合鍵(Composite Key) 由「兩個或兩個以上」欄位所組合而成的鍵。
二.
主屬性（Prime Attribute）屬於某個候選鍵的屬性
非主屬性（Non-prime Attribute）：不屬於任何候選鍵的屬性
---------------------------------------------------------------------------
阿姆斯壯公理
反身律
Y ⊆ X ⇒ X → Y，一個集合可決定它的子集（顯然相依）
擴充律
X → Y ⇒ XZ → YZ，兩邊同時加入屬性，相依仍成立
遞移律
(X → Y、Y → Z) ⇒ X → Z

資料庫設計概念：
A. 實體關聯模型：
1. 實體：資料庫要儲存的對象
  1. (強)實體：矩形(橢圓邊的長方形)
  2. 弱實體：雙線矩形，需依附其他實體
2. 屬性：描述實體的特徵
  1. 一般屬性：橢圓
  2. 多值屬性：雙線橢圓，ex. 電話
  3. 導出屬性：虛線橢圓，可由其他值推算 ex. 年齡
  4. 主鍵屬性：橢圓內的文字加底線。
3. 關係：實體與實體之間的關聯
  1. 關係：菱形，實體間的關聯
  2. 識別關係：雙線菱形，連接弱實體
----
B. 轉換成 關聯表的規則：
一. 實體：
  1. 強實體：直接轉換成一個獨立的資料表。實體中的屬性變成欄位，原本的鍵值屬性 (Key Attribute) 變成該表的主鍵 (Primary Key, PK)。
  2. 弱實體：轉換成資料表，但它的主鍵必須由「自己的部分鍵 (Partial Key)」加上「所依附之強實體的主鍵」合併組成（複合主鍵）。
二. 屬性：
  1. 單值屬性：直接變成資料表的欄位。
  2. 複合屬性：必須拆解成獨立欄位。例如：「地址」不該是一個欄位，要拆成「縣市」、「區」、「街道」等三個欄位。
  3. 多值屬性：必須為它建立一個「新的資料表」，新表的主鍵由「原實體的主鍵」加上「多值屬性本身」共同組成。
  4. 衍生屬性：通常不存入資料庫中（例如：「年齡」可由「生日」計算得出）。
三. 關係：
  1. 1:1：將其中一方的主鍵 (PK) 放入另一方作為外鍵 (FK)
  2. 1:N：永遠將「1」那一方的主鍵，放進「N」那一方的資料表中作為外鍵。
  3. M:N：必須建立一張新的「中介表」。將兩方的主鍵都拉進這張新表作為外鍵，且這兩個外鍵通常會共同組成新表的複合主鍵。
----
C. 界定功能相依性：將文字轉化為嚴謹的FD方程式，利用箭頭表示 一對一 或 一對多的關係
ex. FD1(小寫1): 醫生代號 → {姓名, 診間號碼}，表示醫生代號決定 姓名、診間號碼
----
D. 推導各表的候選鍵(利用屬閉包，把每一個表的候選鍵都選出來)
屬性閉包，給定一組屬性，從它「能推導出的所有屬性」的集合，就是它的閉包。
若一個屬性 K 在關係 R 的閉包 K^+ 包含 R 的所有屬性，且其任何真子集（Proper Subset）的閉包都不包含所有屬性，則 K 稱為候選鍵。
ex. 資料表 R(A,B,C,D,E,F)，函數相依集F(A>B,B>C,AC>D)。計算屬性集合 {A}的閉包，求A^+ ?
ABCD

正規化檢驗：
一. 好的正規化特質：
  1. 無損分解，分解後的表格，用自然合併組回去，結果與原表完全一樣，沒有遺失資料，也沒有多出虛假的資料組合。
    * 自然合併，以兩表中的同名且同型的欄位為合併條件，把這些欄位值相同的列組合起來，用來合併的同名欄位在結果中只保留一份。
  2. 功能相依性保持(最好)，分解前擁有的所有功能相依，於分解後的各子表中仍能保留與檢察。
    * 缺乏相依保持「不會」在分解當下產生虛假資料，但會讓後續的寫入／更新中，某些規則難以驗證與維持。
    * 處理（無法保持時，以下擇一處理）：
      (1) 反正規化退回較低正規化（如 3NF）；
      (2) 在應用程式或觸發器（trigger）額外撰寫邏輯，於寫入／更新時檢查。
二. 正規化階梯：
  * 1NF. 關聯表中每一個屬性的值皆具原子性(不可再分得基元值)，也就是非多值、非複合屬性。
      處理方式，多值，分解成多列 或 另立表；複合屬性 則可拆為簡單屬性。
  * 2NF. 
      1. 消除非鍵屬性對主鍵的部分功能相依，確保所有非鍵屬性皆完全相依於整個（複合）主鍵。
      2. 自動符合的情況：
        1. 主鍵只有一個欄位，自動符合。
        2. 沒有非主鍵欄位，自動符合。 
      3. 處理方式，把部分相依的非鍵屬性，連同其決定因素抽出、建立新關聯（決定因素當新表主鍵），原表刪除該相依因素，並設外來鍵。
  * 3NF. 
      1. 消除非鍵屬性對鍵的遞移功能相依（每一個非鍵屬性，都只能直接依賴主鍵，不能依賴其他非鍵屬性）
      2. 自動符合：
        1. 最多只有「一個」非主鍵欄位，自動符合。
        2. 沒有非主鍵欄位（全表皆為主鍵），自動符合。
      3. 處理方式：把遞移相依中「非鍵的決定因素＋其相依因素」抽出、建立新關聯，原表刪除相依因素，並設外來鍵。
  * BCNF，
    1. 確保每一條非顯然功能相依的決定因素，皆為超鍵。(所有的功能相依（箭頭左邊）皆為該表的候選鍵)
        非顯然功能相依，功能相依 X → Y 中,箭頭右邊 Y 至少包含一個不屬於左邊 X 的屬性,稱為非顯然功能相依。
    2. 自動符合
      1. 若一張表只有單一候選鍵（尤其是單一屬性），那它只要是 3NF 就自動是 BCNF。
      2. 資料表總共只有兩個欄位
    3. 處理方式；找出違反的函數相依 X → Y（X 非超鍵），將 {X 及 Y} 取出另立新關聯（X 為主鍵），原關聯刪除 Y、保留 X 作為外來鍵。此分解保證無損，但可能犧牲相依保存。
  * 4NF，不存在多值相依。
   多值相依：一個鍵決定某屬性的「一組值」，且該組值與另一獨立屬性互不相干
  * 5NF，消除合併相依，確保資料表不能再被無損分解為更小的表。
三. 反正規化：
  1. 正規化的缺點：
    1. 查詢效能低落，高度正規化會將資料過度拆解至多張表，當程序需要檢視完整資訊時，需要大量表格連接(join)，會造成查詢速度變慢。
    2. 系統結構過度複雜，過度拆解很容易造成，會導致開發與維護成本大幅提升。
  2. 使用時機：
    1. 讀取時機多、但寫入時機少；
    2. 需要頻反存取"衍生欄位"，比如訂單系統的總金額，若嚴格遵守，每次查詢動態計算，太耗費資源。

CREATE TABLE student_profile (
  profile_id  INT           PRIMARY KEY,                         -- 整數＋主鍵
  student_id  CHAR(8)      NOT NULL UNIQUE,                      -- 一欄多約束
  name        VARCHAR(20)  NOT NULL,                             -- 變長文字＋非空
  gender      CHAR(1)      DEFAULT 'F' CHECK (gender IN ('M', 'F')),
  score       DECIMAL(5,2) DEFAULT 0 CHECK (score BETWEEN 0 AND 100),
  birth_date  DATE          NOT NULL,
  created_at  DATETIME      DEFAULT '2026-01-01 09:00:00',
  FOREIGN KEY (student_id) REFERENCES student(id) 
 ON DELETE CASCADE（子表一起刪）、SET NULL（子表設為空）、RESTRICT（禁止刪除）。
);
