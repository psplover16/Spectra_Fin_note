# 正規化

> 科目：資料庫｜正規化幾乎是資料庫設計**必考**，申論常出「這張表違反第幾正規化、請拆到 3NF」「3NF 與 BCNF 差在哪」。它是把一張「什麼都塞在一起」的爛表，一步步拆成乾淨、不重複、不出錯的多張表的方法。
>
> 學習方式：各正規化的**定義與要除掉的異常**屬【理解】；**判斷 → 拆解**的步驟要能實際操作【練習】；「無損／相依保持」與「3NF、BCNF 保證什麼」這幾句結論屬【硬背】。

---

## 🎯 開場題目

> 考題常這樣問：
>
> 1. 表 `選課(學號, 課號, 成績, 課名)`，主鍵 `{學號, 課號}`，其中「課號 → 課名」。這違反第幾正規化？該怎麼拆？
> 2. 「**3NF 和 BCNF 差在哪**？為什麼實務上有時『做到 3NF 就好』？」
> 3. 「一個好的分解要具備**哪兩個性質**？哪個是必備、哪個是最好有？」

先自己想想再往下看。

---

## 🤔 先想想

- 正規化從頭到尾都在問兩件事：「**誰決定誰**（功能相依）」與「**誰是鍵**」。
- 每升一階，就多除掉**一種資料異常**；而且**高階一定先滿足低階**（想做 3NF 得先是 2NF、1NF）。
- 拆表不能拆壞：拆完要能**無損接回來**，不能遺失資料、也不能多出虛假的資料組合。

---

## 📖 觀念拆解

### 一、先把「鍵」的術語講清楚

正規化全程都在問「哪個屬性被哪個屬性決定」「誰是鍵」，所以先釐清鍵的術語：

| 術語 | 定義 |
|---|---|
| **外來鍵** Foreign Key | 某欄位（或欄位組合），其值**參考另一張表的主鍵**，用來把兩張表串接、建立關聯 |
| **超鍵** Superkey | 能**唯一識別**一列的欄位組合，**可以帶多餘欄位** |
| **候選鍵** Candidate Key | **最小的超鍵**（拿掉任一欄就不再唯一）；每個都有資格當主鍵 |
| **主鍵** Primary Key | 被選來唯一識別每筆紀錄的**那一個候選鍵** |
| **替代鍵** Alternate Key | 沒被選為主鍵的候選鍵 |
| **鍵（主）屬性** Prime | 只要一個欄位**屬於任何一個候選鍵**，它就是鍵屬性 |
| **非鍵（主）屬性** Non-prime | **不屬於任何候選鍵**的欄位 |

📌 **包含關係（超常考）**：`主鍵 ⊆ 候選鍵 ⊆ 超鍵`。候選鍵是「最小的超鍵」，主鍵是「被選中的候選鍵」。此外，外來鍵也可以指向**同一張表**的主鍵（自我參考），例如員工表的「主管」欄位指向同表的員工編號。

### 二、好的分解要具備的兩個性質

拆表是正規化的動作，但拆得好不好，看這兩個性質：

**（一）無損分解（Lossless-join）—— 必備**

表格分解後，用**自然合併（Natural Join）**組回去，結果要與原表**完全一樣**：沒有遺失資料，也沒有多出虛假的資料組合。

- **自然合併**：以兩表中**同名且同型**的欄位為合併條件，把這些欄位值相同的列組合起來；用來合併的同名欄位在結果中**只保留一份**。
- 若兩表**沒有同名欄位**，自然合併會退化成**笛卡兒乘積**（每列兩兩相配）—— 這正是虛假資料的來源。

> 💡 無損其實「一定做得到」：只要拆解時讓「**共同欄位是其中一張子表的鍵**」就保證無損。標準正規化的拆法（抽出「決定因素＋相依因素」、決定因素當新表主鍵、原表保留外來鍵）**每一步本來就是無損**，不必靠反正規化補救。

**（二）功能相依性保持（Dependency Preservation）—— 最好具備**

分解前擁有的**所有功能相依**，於分解後的各子表中**仍能保留與檢查**（不必把表 join 回去才驗證）。

每條相依往往反映一條**業務規則**；若分解後失去，可能允許不合邏輯的操作、造成資料不一致。與無損的差別：**缺乏相依保持「不會」在分解當下產生虛假資料**，但會讓**後續**寫入／更新時，某些規則難以驗證與維持。無法保持時的處理：(1) **反正規化**退回較低正規化（如 3NF）；或 (2) 在**應用程式或觸發器（trigger）**額外寫檢查邏輯。

> ★ **最關鍵的一句**：**3NF 保證「無損」＋「功能相依性保持」兩者都有；BCNF 保證「無損」，但「功能相依性保持」不一定有。** 這就是為什麼有時「停在 3NF 就好」——硬做到 BCNF 可能犧牲某條相依（規則），這時才用反正規化／觸發器補回。

### 三、正規化階梯（總覽）

由低到高，**每一階都比下一階多除去一種異常**，且**高階必須先滿足低階**：

| 階 | 名稱 | 除去什麼 |
|---|---|---|
| 1NF | 第一正規化 | 值具**原子性**（去多值、複合） |
| 2NF | 第二正規化 | 去除**部分相依** |
| 3NF | 第三正規化 | 去除**遞移相依** |
| BCNF | Boyce-Codd | **決定因素皆為超鍵** |
| 4NF | 第四正規化 | 去除**多值相依** |
| 5NF | 第五正規化 | 去除**合併相依** |

BCNF 介於 3NF 與 4NF 之間；做到某一階，前面各階都須已滿足。

📌 **正規化到底在消除什麼**：未正規化（有冗餘）的表會產生**三大異常**——**插入異常**（想新增資料卻因缺其他欄位而無法寫入）、**刪除異常**（刪一列連帶失去不相關的資訊）、**更新異常**（同一資訊多處重複，改一處就前後不一致）。正規化拆表正是為了根除這三種異常。

### 四、第一正規化 1NF（除去重複資料項目）

- **要求**：關聯表中**每一個屬性的值皆具原子性**，也就是**非多值、非複合屬性**。
- **處理方式**：多值 → 分解成多列或另立表；複合屬性 → 拆為簡單屬性。

**範例（違反）**：

| 學號 | 姓名 | 電話 |
|---|---|---|
| S01 | 王小明 | 0912-111、0922-222 |
| S02 | 李小華 | 0933-333 |

問題：S01 的「電話」一格塞了兩個值，**違反 1NF**（欄位值不是單一值）。

**處理後**（把電話另立一張表，每格只放單一值）：

- 學生（<u>學號</u>、姓名）
- 學生電話（<u>學號 FK</u>、<u>電話</u>）　主鍵 = {學號, 電話}

### 五、第二正規化 2NF（除去部分相依）

- **要求**：滿足 1NF，且**每個非鍵屬性都「完全功能相依」於鍵**（即沒有部分相依）。
- **處理方式**：把部分相依的非鍵屬性，連同其**決定因素**抽出、建立新關聯（決定因素當新表主鍵），原表**刪除該相依因素**，並設外來鍵。

> 💡 兩個精確化：① 嚴格定義是針對**候選鍵**，非只有主鍵；碰到多候選鍵的題目要用候選鍵。② **部分相依只可能發生在「複合鍵」**——主鍵若是單一屬性，沒有「一部分」可被相依，**自動滿足 2NF**。

**範例**：原表 `選課(學號, 課號, 成績, 課名)`，主鍵 = {學號, 課號}。功能相依：

- `{學號, 課號} → 成績`　需要兩個鍵才能決定 → 完全相依（OK）
- `課號 → 課名`　只靠課號就能決定 → **部分相依（違反 2NF）**

為何違反：課名只依賴主鍵的「**一部分**」（課號），不是整個主鍵。

**處理後**（把「課號＋課名」抽出另立表，原表保留課號當外來鍵）：

- 選課（<u>學號</u>、<u>課號</u>、成績）　課號 為 FK → 課程
- 課程（<u>課號</u>、課名）

### 六、第三正規化 3NF（除去遞移相依）

- **要求**：滿足 2NF，且**不存在非鍵屬性遞移相依於鍵**；也就是**非鍵屬性之間不存在功能相依**（非鍵屬性不互相決定）。
- **處理方式**：把遞移相依中「**非鍵的決定因素＋其相依因素**」抽出、建立新關聯，原表刪除相依因素，並設外來鍵。

> 💡 形式定義（進階）：對每一條非顯然相依 `X → A`：**X 是超鍵，或 A 是主屬性**。注意「或 A 是主屬性」這個例外，就是 3NF 與 BCNF 的分水嶺。

**範例**：原表 `學生(學號, 系所, 系主任)`，主鍵 = {學號}。功能相依：

- `學號 → 系所`（學生屬於某系）
- `系所 → 系主任`（系決定系主任）
- ⇒ 推得 `學號 → 系主任`，為**遞移相依**

為何違反：系主任（非主屬性）透過「系所」間接依賴主鍵，即依賴**另一個非主屬性**。

**處理後**（把「系所＋系主任」抽出另立表，原表保留系所當外來鍵）：

- 學生（<u>學號</u>、系所 FK）
- 系所（<u>系所</u>、系主任）

### 七、BCNF（Boyce-Codd 正規化）

- **定義**：屬於 3NF 的加強，**一定符合 3NF**。要求**每一條非顯然功能相依的決定因素皆為超鍵**。

> ★ BCNF 真正嚴在哪：比較兩者對每條 `X → A` 的要求——
> - **3NF**：X 是超鍵 **或 A 是主屬性**　←　有一個「逃生門」
> - **BCNF**：X 是超鍵　←　**拿掉了「或 A 是主屬性」這個逃生門**
>
> 兩者用的都是「超鍵」。BCNF 更嚴，是因為它**取消了 3NF「被決定的是主屬性就放行」的例外**。（「超鍵」比「候選鍵」更寬，候選鍵本來就是超鍵的一種，所以用超鍵不是收緊。）

**何時 3NF 與 BCNF 才會不同**：只有在表中**存在多個、互相重疊的複合候選鍵**時，兩者才會不同。若一張表只有**單一候選鍵**（尤其是單一屬性），那它只要是 3NF 就**自動是 BCNF**。

**經典例（符合 3NF 但違反 BCNF）**：`指導(學生, 科目, 老師)`，已知 `{學生,科目} → 老師`、`老師 → 科目`。候選鍵為 {學生,科目} 與 {學生,老師}（**重疊在「學生」**），故學生、科目、老師皆為主屬性。

- 檢查 `老師 → 科目`：老師不是超鍵，但**科目是主屬性 → 符合 3NF**。
- 同一條 `老師 → 科目`：老師不是超鍵 → **違反 BCNF**。

**處理方式**：把「不為超鍵的決定因素＋其相依因素」抽出另立表、原表刪除相依因素、再決定外來鍵。依 `老師 → 科目` 拆解後：

- 授課（<u>老師</u>、科目）
- 指導（<u>學生</u>、<u>老師</u>）

> 💡 BCNF 的代價：此分解**無損，但不保功能相依性保持**——原相依 `{學生,科目} → 老師` 會跨兩張表、**無法保存**，這正是「停在 3NF」的取捨點。

### 八、4NF、5NF 與反正規化

- **第四正規化 4NF**：滿足 BCNF，且不存在**多值相依（Multivalued Dependency）**。多值相依：一個鍵決定某屬性的「一組值」，且該組值與另一獨立屬性互不相干。例：員工有多個技能、又有多個語言，兩者彼此獨立 → 應拆成「員工–技能」與「員工–語言」兩表，避免兩兩交叉產生冗餘。
- **第五正規化 5NF**：滿足 4NF，且不存在無法由候選鍵推得的**合併相依（Join Dependency）**。處理：拆成更小的投影，使其能**無損合併**還原。（國考多僅須知定義與層級）
- **反正規化（Denormalization）**：為了**查詢效能**，刻意違反正規化、加入**冗餘**（如預先 join 好、加入計算欄位），以減少 join、加快讀取；代價是增加冗餘與**更新異常風險**。常用於讀多寫少、報表查詢的場景。

---

## ✅ 回到題目：解答

1. `課號 → 課名` 只靠主鍵的一部分（課號）→ **部分相依 → 違反 2NF**。拆成：選課(<u>學號</u>,<u>課號</u>,成績) ＋ 課程(<u>課號</u>,課名)，課號在選課表當外來鍵。
2. **BCNF 取消了 3NF「或 A 是主屬性」這個逃生門**，要求每個決定因素都是超鍵，比 3NF 嚴。硬做 BCNF 可能失去某條功能相依（相依保持），造成規則難維持，所以有時「停在 3NF」——因為 3NF 同時保證無損＋相依保持。
3. **無損分解（必備）** ＋ **功能相依性保持（最好有）**。

---

## 📌 重點整理

- 包含關係：`主鍵 ⊆ 候選鍵 ⊆ 超鍵`；鍵（主）屬性＝屬於任一候選鍵的屬性。
- **無損分解＝必備**（join 回去與原表相同、無虛假列）；無同名欄位 → 退化成**笛卡兒乘積**。
- **功能相依性保持＝最好有**；缺它不會當下產生虛假資料，但後續規則難維持。
- **3NF 保證 無損＋相依保持；BCNF 保證無損、但相依保持不一定。**
- 各階去除的異常：**1NF** 原子性、**2NF** 去部分相依（只發生在複合鍵）、**3NF** 去遞移相依、**4NF** 去多值相依、**5NF** 去合併相依。
- **BCNF**：每個決定因素皆為**超鍵**；比 3NF 嚴（少了「或 A 是主屬性」的例外）；3NF≠BCNF 只在**重疊的複合候選鍵**時發生。

---

## ⚠️ 常見陷阱

- **2NF 只針對複合鍵**：主鍵是單一屬性時，不可能有部分相依，自動滿足 2NF。別在單一主鍵的表硬找部分相依。
- **遞移相依看「非主屬性互相決定」**：`學號 → 系所 → 系主任`，違反的關鍵是「系主任靠另一個非主屬性系所」。
- **BCNF 不是「候選鍵 vs 超鍵」的差別**：兩者標準都用超鍵；BCNF 嚴在取消了 3NF 的例外，不是把超鍵換成候選鍵。
- **無損 ≠ 相依保持**：BCNF 分解一定無損，但可能失去相依保持；別把兩者混為一談。
- **反正規化是刻意退步**：為效能加冗餘，代價是更新異常風險，不是「正規化失敗」。

## 📝 練習題（含解答）

**Q1.** `員工(員工號, 姓名, 部門號, 部門名)`，主鍵 {員工號}，已知 `員工號 → 姓名, 部門號`、`部門號 → 部門名`。違反第幾正規化？如何拆？
<details><summary>看解答</summary>

單一主鍵，無部分相依（自動滿足 2NF）。但「部門名」靠非主屬性「部門號」→ **遞移相依，違反 3NF**。拆成：員工(<u>員工號</u>, 姓名, 部門號 FK)、部門(<u>部門號</u>, 部門名)。

</details>

**Q2.** 為什麼「無損分解」永遠做得到，而「功能相依性保持」不一定？
<details><summary>看解答</summary>

只要拆解時讓共同欄位是其中一張子表的鍵，就保證無損；標準拆法（抽出決定因素＋相依因素、決定因素當新表主鍵）本來每步都無損。但相依保持要求所有 FD 都能在單一子表內檢查，某些相依（尤其做 BCNF 時）會被拆到跨兩張表，就無法保存。

</details>

**Q3.** 一張表只有**單一候選鍵**，它是 3NF，那它是 BCNF 嗎？
<details><summary>看解答</summary>

**是**。3NF 與 BCNF 只有在「存在多個、互相重疊的複合候選鍵」時才會不同；單一候選鍵（尤其單一屬性）的表，只要是 3NF 就自動是 BCNF。

</details>

**Q4.** 自然合併（Natural Join）時，如果兩張子表「沒有同名欄位」會發生什麼？
<details><summary>看解答</summary>

會退化成**笛卡兒乘積**（每列兩兩相配），產生大量虛假的資料組合 → 這就是「有損」分解，違反無損的要求。

</details>

**Q5.** `指導(學生, 科目, 老師)`，`{學生,科目} → 老師`、`老師 → 科目`。它符合 3NF 嗎？符合 BCNF 嗎？為什麼？
<details><summary>看解答</summary>

候選鍵為 {學生,科目} 與 {學生,老師}，三個欄位都是主屬性。對 `老師 → 科目`：老師不是超鍵，但科目是主屬性 → **符合 3NF**；然而老師不是超鍵 → **違反 BCNF**。拆成 授課(<u>老師</u>,科目) ＋ 指導(<u>學生</u>,<u>老師</u>)（無損，但不保相依保持）。

</details>
