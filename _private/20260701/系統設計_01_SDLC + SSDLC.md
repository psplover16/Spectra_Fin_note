# SDLC + SSDLC

> 科目：系統分析與設計（歸在資訊管理底下）。這科內容很散，但 SDLC 是**整科的骨架**——先把「一個系統從無到有要經過哪些階段」記牢，其他知識點（開發模型、測試、導入…）都能掛回這條時間線上。

- 系統開發像**蓋房子**：要先規劃、畫設計圖，才動工、驗收、入住、日後保養——不能一開始就砌牆。
- 房子蓋好後，**住進去後的維修保養（維護）**往往比蓋的時候還花錢、花時間。軟體也一樣。

## 📖 觀念拆解

### 一、SDLC 是什麼？（系統開發生命週期）

**SDLC（System Development Life Cycle，系統開發生命週期）** 是開發資訊系統的**標準階段流程**，從最前面的規劃，一路走到最後的維護。

把它想成一條「系統的一生」：從構想誕生、被打造出來、上線服務，到持續被修修補補——每個階段都有明確要做的事，以及主要負責的人。

七個階段如下表（**順序要背**）：

| 階段 | 在做什麼 | 誰主導 |
|---|---|---|
| 規劃 Planning | 確定目標、可行性分析 | 管理層 |
| 分析 Analysis | 蒐集需求、了解現況 | 系統分析師 |
| 設計 Design | 設計系統架構、資料庫、介面 | 設計師 |
| 實作 Implementation | 寫程式 coding | 程式設計師 |
| 測試 Testing | 驗證功能正確 | 測試 |
| 導入 Deployment | 系統上線 | 專案團隊 |
| 維護 Maintenance | 修錯、更新 | 維護團隊 |

📌 **看懂表裡的白話：**
- 「**可行性分析**（規劃）」＝先評估「這專案值不值得做、做不做得到」（技術、成本、時程可不可行），再決定要不要投入。完整來說共**五種可行性**：除了技術、經濟（成本效益）、時程，還有**操作**（人員／流程能否配合）與**法律**（法規是否允許）。
- 「**分析**」和「**設計**」常被搞混：分析是**問「要做什麼」（What）**，蒐集需求、了解現況；設計是**回答「怎麼做」（How）**，把需求轉成架構、資料庫、介面的藍圖。
- 「**維護**」不是做完就沒事——修 bug、因應法規或需求更新，會持續整個系統壽命。**維護通常佔整個生命週期成本最大的一塊**（這點超常考）。維護還常細分四類：**改正性**（修 bug）、**適應性**（因應環境／法規變動）、**完善性**（增強功能，通常佔比最大）、**預防性**（預先防範未來問題）。

### 二、常見開發模型

同樣是走完 SDLC，**要用什麼節奏、什麼順序走**，就衍生出不同「開發模型」。考題最愛考各模型的**特色**與**適用情境**。

| 模型 | 特點 | 優缺 |
|---|---|---|
| 瀑布 Waterfall | 線性，一階段完成才下一階段 | 文件清楚但難應對需求變更 |
| 雛形 Prototyping | 先做簡單原型給使用者看 | 早確認需求但可能東拼西湊 |
| 螺旋 Spiral | 瀑布加原型加風險分析，反覆迭代 | 適合大型高風險但成本高 |
| 敏捷 Agile | 小步快跑、反覆交付 | 適應變更快但文件較少 |

📌 **白話拆解與例子：**
- **瀑布**：像水往下流、不回頭。規劃 → 分析 → 設計 →…一階段**做完才進下一階**。文件最齊全，但做到一半客戶改需求，就很難回頭改。適合需求明確、變動少的專案。
- **雛形**：先做一個**陽春版原型**（例如只有畫面、按鈕沒功能）給使用者看，快速確認「你要的是不是這樣」。好處是需求早對焦，但原型若一路將就沿用，容易變成「東拼西湊」的架構。
- **螺旋**：把瀑布＋雛形，再加上**風險分析**，一圈一圈**反覆迭代**，每繞一圈就評估一次風險。適合**大型、高風險**的專案（如國防、金融核心），但一圈圈跑下來成本高。
- **敏捷**：**小步快跑**，把大專案切成一個個短週期（衝刺），**反覆交付**可用的小成果。能快速適應需求變更，但相對**文件較少**。

### 三、SSDLC：把資安「內建」進每一階段

**SSDLC（Secure SDLC，安全系統開發生命週期）** 的核心一句話：**在 SDLC 的每一個階段都融入資安，而不是等系統做完才回頭補**。

兩個關鍵口號：
- **Security by Design（安全內建 / 設計即安全）**：從設計之初就把安全考量放進去，而非事後加裝。
- **Shift Left（左移）**：把資安活動**往開發流程的「前面（左邊）」移**。因為越早發現漏洞、修復越便宜；拖到上線才爆，代價最大。

每個階段對應的資安活動：

| SDLC 階段 | 融入的資安 |
|---|---|
| 規劃／分析 | 安全需求、風險評估 |
| 設計 | 威脅建模 Threat Modeling、安全架構 |
| 開發 | 安全編碼、程式碼審查 |
| 測試 | 滲透測試、漏洞掃描 SAST/DAST |
| 導入／維護 | 安全設定、持續監控、修補 |

📌 **看懂幾個名詞：**
- **威脅建模（Threat Modeling）**：在設計階段就先想「這系統可能被誰、用什麼方式攻擊」，預先設防。
- **SAST / DAST**：兩種漏洞掃描。SAST＝靜態掃描（不執行程式，直接檢查原始碼）；DAST＝動態掃描（實際跑起來、從外部戳戳看）。
- **滲透測試（Penetration Test）**：模擬駭客實際攻擊，測試防護夠不夠。

## ✅ 回到題目：解答

1. **SDLC 七階段順序 & 成本最大？** → 規劃 → 分析 → 設計 → 實作 → 測試 → 導入 → 維護。其中 **維護** 通常佔生命週期成本最大。
2. **瀑布 vs 敏捷最大差別？** → 瀑布是**線性、一階段完成才下一階段**，文件清楚但難應對需求變更；敏捷是**小步快跑、反覆交付**，適應變更快但文件較少。
3. **SSDLC 差在哪？口號意思？** → SSDLC 是在**每個階段都內建資安**，不是做完才補。**Security by Design**＝安全從設計就內建；**Shift Left**＝把資安活動往前移，越早做越省。

---

## 📌 重點整理

- **SDLC 七階段（順序硬背）**：規劃 → 分析 → 設計 → 實作 → 測試 → 導入 → 維護。
- **維護通常佔生命週期成本最大**（常考）。
- **四大開發模型**：瀑布（線性）、雛形（先給原型）、螺旋（瀑布＋原型＋風險分析、迭代）、敏捷（小步快跑）。
- **SSDLC**：每階段內建資安，不是事後補；兩口號＝**Security by Design**、**Shift Left**。
- 分析問 **What（做什麼）**，設計問 **How（怎麼做）**。

---

## ⚠️ 常見陷阱

- **階段順序別跳**：常見陷阱把「測試」擺到「導入」後面。正確是**先測試、再導入（上線）**。
- **成本最大是「維護」不是「開發」**：直覺以為寫程式最花錢，但長期看維護才是最大宗。
- **分析 vs 設計別混**：分析＝需求（做什麼）；設計＝藍圖（怎麼做）。
- **Shift Left 方向別記反**：是把資安「往左（往前）」移到開發早期，不是拖到最後。
- **SSDLC ≠ 做完再補資安**：它強調「每階段都要有資安」，這正是它和普通 SDLC 的差異。
